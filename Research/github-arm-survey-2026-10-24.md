# Rig Kontrol 3 on Apple Silicon: public implementation survey

Reviewed 24 October 2026. Tracked by `rigkontrol3-tw5.2`.

## Finding

There is a directly relevant public implementation: **[mihaimetal/rk3-coreaudio](https://github.com/mihaimetal/rk3-coreaudio)** provides an Apple Silicon userspace audio and MIDI stack, a published binary release, a shared USB owner, and a separate MIDI helper. It deserves evaluation before further independent audio/coexistence development. Its current MIDI destination handles tempo clock, however, rather than effect-state CC feedback. It does not remove the need to obtain actual Guitar Rig state from a host. [Pinned README](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/README.md), [MIDI receive implementation](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_midi.c#L725-L759).

The earlier local research already identified Timebutt's web bridge and rstets' Linux controller. This refresh adds a newer, directly relevant macOS ARM stack and examines what each project's LED support actually means. This was a focused survey, not an exhaustive inventory of all GitHub code. No third-party product code was copied, built, installed, or run; no hardware commands were sent.

## Direct Apple Silicon candidate: rk3-coreaudio

The maintainer documents stereo input/output at 44.1, 48, 96 and 192 kHz, nine switches, the built-in expression pedal, two external expression inputs, and MIDI operation while audio is idle. Its June 23 release, [v1.0.0](https://github.com/mihaimetal/rk3-coreaudio/releases/tag/v1.0.0), points to [`041664df02639e7bf3a9a690afe90b1703739aab`](https://github.com/mihaimetal/rk3-coreaudio/commit/041664df02639e7bf3a9a690afe90b1703739aab). The later inspected master revision contains additional features, so the latest README must not be assumed to describe every file in that older binary archive. [README](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/README.md).

This is more than an ARM-labelled README: the source implements an IOUSBLib transport, an AudioServer plug-in, and a CoreMIDI helper; CI and release workflows target a macOS runner identified as Apple Silicon. These are implementation/build evidence. This survey did not inspect the downloaded binary's architecture or independently reproduce hardware operation. [USB transport](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/usb_iokit.c), [build](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/Makefile), [CI](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/.github/workflows/ci.yml), [release workflow](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/.github/workflows/release.yml).

Its shared engine owns USB and relays controller reports over loopback UDP to a normal-user MIDI helper. A reverse socket relays complete LED/display states to USB. This addresses the audio/controls ownership conflict that separate libusb clients would face. [Relay definitions](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_midi.h#L28-L49), [engine](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_engine.c), [helper](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/tools/rk3midihelper.c).

### What its LEDs and ninth switch actually support

The incoming CoreMIDI callback recognizes clock, start, continue and stop bytes. Other bytes are ignored. It does not decode incoming effect-state CCs. The LED utility accepts an explicit raw state from its caller; that is a useful hardware control interface, not discovery of Guitar Rig state. [Clock callback](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_midi.c#L725-L759), [LED utility](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/tools/rk3led.c).

Tempo flashes send display bytes, and the engine zero-pads them into a complete output frame. A new effect-state LED writer would need coordinated state merging so tempo updates do not clear switch LEDs. This is an inference from the two write paths, not a hardware test performed here. [Display flash](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_midi.c#L714-L722), [LED frame handling](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_engine.c#L781-L820).

The decoder reads nine digital bits. Printed switch 9 corresponds to bit 8: packet byte 2, bit 0. Its default mapping emits CC28 for that switch. This supplies a concrete protocol hypothesis for our currently unmapped toe switch; it does not establish that our unit actually emits the bit. The same source suppresses the first digital report and uses a treadle default range of 40–270, so its attachment and calibration behavior must be checked against our captures rather than copied blindly. [Mapping and calibration defaults](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_midi.c#L65-L100), [digital decoder](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/rk3_midi.c#L238-L257).

An open [latency PR #1](https://github.com/mihaimetal/rk3-coreaudio/pull/1), head [`4e775d9ec093e7f17b4648c83e3a33cba3baefe7`](https://github.com/mihaimetal/rk3-coreaudio/tree/4e775d9ec093e7f17b4648c83e3a33cba3baefe7), reports 8.6–9.1 ms analog round-trip latency at 48 kHz/64 frames and a handshake fix. It was open and unmerged when checked. The author still lists a long session under real DAW load as untested. Its latest workflow result was `action_required`, not a passing CI result; do not present the PR's claims as independently verified performance. [Workflow run](https://github.com/mihaimetal/rk3-coreaudio/actions/runs/38139431320).

The project is GPL-2.0; its licensing and derivation differ from an independently authored implementation. No code was incorporated during this survey. [License](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/LICENSE).

## Other RK3 implementations

**Timebutt/rig-kontrol-web** uses WebUSB to claim interface 0 and WebMIDI to emit switch notes and expression CC1. The inspected application code reads eight switch bits and expression bytes 5–6. It has no incoming MIDI handler or LED USB write path. The repository also includes a Tauri scaffold, but the inspected revision supplies no demonstrated native macOS ARM build/release. No explicit license file was found in its tree. Useful as packet/mapping precedent, not a verified replacement for the current native driver. [README](https://github.com/Timebutt/rig-kontrol-web/blob/6645acff619a994293110eba518a1085113f008b/README.md), [actual application](https://github.com/Timebutt/rig-kontrol-web/blob/6645acff619a994293110eba518a1085113f008b/src/app/app.component.ts), [tree](https://github.com/Timebutt/rig-kontrol-web/tree/6645acff619a994293110eba518a1085113f008b).

**rstets/rigkontrol3-linux-midicontroller** converts Linux input events into ALSA MIDI and documents Raspberry Pi OS configuration. It relies on Linux's existing caiaq/input stack rather than supplying a macOS USB driver. Its inspected C program emits notes and expression CCs; it does not implement host-state LED reception. No explicit license file was present in the inspected tree. Useful historical Linux precedent, not evidence of macOS ARM support. [README](https://github.com/rstets/rigkontrol3-linux-midicontroller/blob/77f7091afb856ca6e2500c17e4e51a262b478c09/README.md), [source](https://github.com/rstets/rigkontrol3-linux-midicontroller/blob/77f7091afb856ca6e2500c17e4e51a262b478c09/rigkontrol3d.c).

**davecoates/rk3-midi** targets Windows WinUSB and loopMIDI, with audio intentionally excluded. Its documentation explicitly acknowledges that local LEDs can disagree after mouse changes in the plug-in. Configured preset-state resets are predictions, not live host feedback. The service and MIDI adapter confirm an output-only design. Its protocol notes, reconnect tests and configurable mapping are useful comparison material, but this is not macOS ARM support and does not meet the requested LED truth requirement. [README](https://github.com/davecoates/rk3-midi/blob/b5fa8bc26137194812de441225fd27199ca95e95/README.md), [service](https://github.com/davecoates/rk3-midi/blob/b5fa8bc26137194812de441225fd27199ca95e95/src/rk3_midi/service.py), [MIDI adapter](https://github.com/davecoates/rk3-midi/blob/b5fa8bc26137194812de441225fd27199ca95e95/src/rk3_midi/midi_output.py).

## Related implementations worth reusing as architecture references

**Opa-/x1-mk1-usb2midi** is for Traktor Kontrol X1, not RK3. It creates matching-name virtual source/destination ports and routes incoming host MIDI into a USB LED queue. Its CI builds `aarch64-apple-darwin`; the maintainer reports M2 Pro use. This is a concrete example of the bidirectional host-feedback architecture needed here. It does not provide Guitar Rig standalone state or RK3 packet definitions. Apache-2.0. [Source](https://github.com/Opa-/x1-mk1-usb2midi/blob/f9ca9e980a4bebe5b870dafad988a39065c574bb/src/x1_process.rs), [ARM workflow](https://github.com/Opa-/x1-mk1-usb2midi/blob/f9ca9e980a4bebe5b870dafad988a39065c574bb/.github/workflows/rust.yml), [license](https://github.com/Opa-/x1-mk1-usb2midi/blob/f9ca9e980a4bebe5b870dafad988a39065c574bb/LICENSE).

**fersantxez/OpenA8DJ** targets Audio 8 DJ. Its documented shipping path uses a HAL, IOUSBHost and CoreMIDI, with inter-process communication to a shared USB owner. Its DriverKit area is a placeholder, not evidence that a DriverKit driver is required for this family. The implementation is useful for an audio/MIDI ownership comparison but does not support RK3 at the inspected revision. MIT. [Architecture](https://github.com/fersantxez/OpenA8DJ/blob/0a0cf8ba6e9be7c787e2adb4ec1f70574cba55ef/docs/project/architecture.md), [USB source](https://github.com/fersantxez/OpenA8DJ/blob/0a0cf8ba6e9be7c787e2adb4ec1f70574cba55ef/src/hal/OpenA8DJUSB.m).

**RufusIbiza/Encdr** covers other NI controllers and includes an older caiaq Maschine implementation, but no RK3 descriptor was found. Its protocol notes document that EP1 writes can stall unless endpoint 0x81 is drained and reads are queued before writes—relevant corroboration for this project's EP1 lifecycle findings. Its stated macOS ARM hardware verification concerns other models, not RK3. GPL-3.0-or-later. [Protocol notes](https://github.com/RufusIbiza/Encdr/blob/2504b198b6afd5c7f7b624fc4cfe879fc285a522/docs/hardware/ni_maschine_mk1.md), [descriptor](https://github.com/RufusIbiza/Encdr/blob/2504b198b6afd5c7f7b624fc4cfe879fc285a522/encdr/descriptors/ni_maschine_mk1.json), [manifest](https://github.com/RufusIbiza/Encdr/blob/2504b198b6afd5c7f7b624fc4cfe879fc285a522/Cargo.toml).

The separate [NeuRig author site](https://vargaud-labs.com/rig-kontrol-3-mac/) advertises an Apple Silicon MIDI application, but currently says there is no public download and excludes audio from its initial edition. It is not a public GitHub implementation we could inspect or adopt. This is a product-status observation, not a claim about its private code.

## Development implication

Evaluate `rk3-coreaudio` at its pinned source revision before extending our experimental HAL or designing a second shared audio/MIDI owner. A controlled comparison could save substantial transport, sample-rate, audio scheduling, external-pedal and display work. Its installer uses the same `/Library/Audio/Plug-Ins/HAL/RigKontrol3.driver` path as our experimental HAL, so installing it would replace an existing component; this survey deliberately did not do so. [Installer](https://github.com/mihaimetal/rk3-coreaudio/blob/d0679238ad06842f382ef89b995823e978caec9b/install.sh).

For the current MainStage milestone, retain the distinction between hardware LED writes and actual host state. None of the inspected RK3 projects supplies automatic Guitar Rig standalone state discovery. A host must report the real mapped parameter value; the bridge must receive that feedback and serialize LED writes through the USB owner. The X1 project already demonstrates that architectural pattern. The new native feedback destination in this repository can be evaluated against MainStage without replacing the working controller transport.
