# Legacy RK3 audio lifecycle: Intel driver 2.8.0

Static research for `rigkontrol3-do5`, 2026-10-24. **The Intel driver provides concrete startup, format and buffering evidence for a new ARM implementation. It is not an ARM audio backend.** Its device object owns the USB interface and keeps command replies separate from audio-engine start/stop, which supports a single owner serving both audio and controls.

## Rates, format and buffering

`Device::setAudioParams` (`0x2d50–0x2e7d`) builds command `09 [rateCode, depthCode, BPP-low, BPP-high, 01]`. Depth 16 maps to `1`, depth 24 to `2`; other depths map to `0xff`. It resets reply status, sends the command, waits at most about 1000 one-millisecond sleeps, and accepts status **1**. [D `0x2d71–0x2e6c`](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/280-kext-disassembly.txt:2516)

| Rate Hz | 44100 | 48000 | 88200 | 96000 | 192000 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Wire rate code | 0 | 1 | 4 | 2 | 3 |

All five rates are actually offered for RK3, not merely recognized by a generic command encoder: `createNewAudioStream` (`0x4d60`) adds 44100/48000/96000, includes RK3 in the 192000 branch, and includes RK3 in the 88200 branch. The exposed format is stereo signed integer PCM with **24-bit depth/width, big-endian**, mixable. Each stream receives a `0x20000`-byte buffer; `initCoreAudio` (`0x4b20`) declares **0x4000 = 16384 sample frames per buffer**, initially 44100 Hz. These are ring capacities, **not a 16384-frame host I/O quantum or measured latency**. The field layout/endian interpretation is corroborated by the installed Apple SDK's [IOAudioTypes.h](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/IOKit.framework/Headers/audio/IOAudioTypes.h:114>). [D `0x4b38–0x4ba0`, `0x4dbc–0x4e73`, `0x4ed4–0x4fa5`, `0x50fe–0x5119`, `0x51ee–0x520d`](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/280-kext-disassembly.txt:4496)

`performFormatChange` (`0x68d0`) calculates:

`q = floor(rate / 8000) + 11; BPP = min(512, q × wireBytesPerChannel × stereoPairs × 2)`

`wireBytesPerChannel` is 3 for alignment mode 0, otherwise 4 (`initHardware`, `0x53c8–0x53dd`). One stereo pair with nonzero alignment yields BPP 128/136/176/184/280 at the five rates above. This **conditional example** does not establish the RK3's returned alignment solely from static code. After changing pipe policy and obtaining AUDIO_PARAMS success, the engine declares input latency `4q`, output latency `8q` and sample offset `8q` frames. The virtual names are confirmed by relocations at `0x11760`, `0x11758`, `0x11768` respectively. These are driver declarations, not loopback measurements. [D `0x68e1–0x69ae`, `0x6a51–0x6a8c`](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/280-kext-disassembly.txt:6286)

Transfer storage comprises **64 IN / 128 OUT slots**, each with eight `IOUSBLowLatencyIsocFrame` entries (`prepareMemory`, `0x5a8a–0x5abb`; `allocIsocIrps`, `0x70e0`; `clearIsocIrps`, `0x6460`). `queueInIrp` submits eight entries with update frequency 0; `queueOutIrp` submits eight with update frequency 1. The call signatures match Apple's [low-latency IOUSBPipe Read/Write overloads](https://github.com/apple-oss-distributions/IOUSBFamily/blob/main/IOUSBFamily/Headers/IOUSBPipe.h). On this high-speed device, eight microframes correspond to one millisecond; this does not mean all 128 OUT slots are simultaneously queued. [D `0x6700–0x6728`, `0x78df–0x790b`](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/280-kext-disassembly.txt:6131)

Output cadence follows **actual completed IN byte counts**: `readHandler` copies each of the eight IN `frActCount` values into an available OUT slot's requested counts, then queues the next IN and that OUT request. It does not independently round every microframe to a fixed nominal sample count. [D `0x7c28–0x7e40`](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/280-kext-disassembly.txt:7516)

Older evidence is materially consistent with this startup order: 2.6.0 start `0x65b0` has the sentinel call `0x65d6`, initial IN queue `0x67e6`, 64-request bound `0x682d`, then real AUDIO_PARAMS `0x684e`; 2.7.0 start `0x6100` has corresponding calls `0x6126`, `0x6432`, bound `0x648a`, format call `0x64ac`. Both use 200-ms retry sleeps. This is a targeted ordering comparison, not a claim that the engines are byte-identical. [2.6 D](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/260-kext-disassembly.txt), [2.7 D](/Users/zukomgwili/src/rigkontrol3/.build/tmp/legacy-rk3-drivers/270-kext-disassembly.txt)

## ARM implementation consequences and limits

- Keep one USB owner and one continuously multiplexed EP1 reply reader. Audio start/stop should not force the controller app to compete for the interface.
- Make asynchronous command acknowledgement and input priming explicit. The Intel sequence is stronger evidence than write-success alone; bounded retries do not replace interpreting status.
- Preserve IN-driven OUT cadence and mode-specific sample/check-byte handling. Reimplementing these behaviors is useful; copying Intel object layouts or kernel API assumptions is not.
- Treat the legacy `+11` BPP margin as a comparison point: the pinned public engine uses `+5` in [caiaq_compute_bpp](/Users/zukomgwili/src/rigkontrol3/.build/upstream/rk3-coreaudio/caiaq_protocol.c:81). Neither the old queue depths nor its declared latency proves safe/optimal user-space HAL scheduling. Benchmark audio continuity and measured latency on this Mac before changing transfer granularity.
- This trace does not establish complete sample-codec correctness, unplug/replug recovery, a firmware update requirement or the performance of Apple's user-space low-latency API on ARM. Apple's [IOAudioEngine header](https://raw.githubusercontent.com/apple-oss-distributions/IOAudioFamily/main/IOAudioEngine.h) distinguishes ring size, sample offsets and latency, and directs newer implementations toward AudioServerPlugIn. The report supplies protocol/lifecycle facts, not reusable proprietary implementation code.
